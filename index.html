Várias APIs do código atual quebram ou degradam nessas versões. 2.1 JavaScript — riscos reais Recurso usado Introduzido em Risco no Moto X Situação no código String.padStart Chrome 57 Quebra o relógio Usado em atualizarRelogio e timer Array.includes Chrome 47 Quebra filtros/URLs Vários pontos Element.replaceChildren Chrome 86 Falha silenciosa Já tem fallback (while firstChild) — ok crypto.randomUUID Chrome 92 Fallback existe ok Object.assign Chrome 45 Limite Borderline classList / dataset Antigos Ok na prática Ok Arrow functions / const/let ~45–49 Limite Se o Chrome do aparelho for <49, o script inteiro pode falhar Promise 32+ Ok Ok MediaMetadata / Media Session 73+ Ignorado Já está em try/catch — ok HLS.js + MSE Variável Pode falhar em WebView fraco Há fallback nativo HLS (Safari/iOS) e timeout Google Cast SDK Desktop/Chrome moderno Não roda em Android antigo Já tratado com mensagem Problemas críticos para o Moto X: padStart — sem polyfill o relógio e o sleep timer quebram. includes — várias checagens de host/URL e busca. CSS gap em flex — Chrome só passou a respeitar gap em flex de forma confiável bem depois; em aparelhos antigos os botões ficam colados. CSS Grid (presets YouTube, diagnóstico) — Chrome 57+; em versões anteriores vira “bloco empilhado” (aceitável, mas feio). position: sticky no header — pode não grudar; não quebra o resto. backdrop-filter — já desligado no lite-mode (bom). 2.2 O que o código já faz bem para dispositivos fracos Detecção de deviceMemory / hardwareConcurrency → lite-mode (menos blur, menos animação, HLS com buffer menor). Pool de Audio + invalidação de streams antigos (evita “duas rádios tocando”). Timeouts em conexão de stream (10–12 s). Fallback de URLs múltiplas (CBN, BandNews). YouTube com token de carga (ytLoadToken) para evitar race. Mixed content bloqueado de forma explícita (HTTP em página HTTPS).
